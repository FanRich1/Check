# 业务与技术补充思考

## 1. 费用身份不能只用费用名称

一张账单可能有两行 Handling Charge，金额不同，也可能金额相同。按名称或“名称+金额”直接去重会丢失真实费用。当前结合单据、交易方、货运标识、具体行定位和原始来源哈希；无法消歧时复核。跨扫描版本的稳定费用身份仍需要更丰富的业务 ID。

## 2. OCR 字段与原文是不同证据

OCR 返回的 `chargeList` 可能合并两行，返回成功也可能业务模板全空。当前保留供应商原始响应和版本、区分页面原文与结构化字段，空响应和超时单列错误；图片可显式启用本地辅助识别。下一步可建立真实多版式 OCR 标签集和按字段置信度策略，不能仅凭 success=true 自动记账。

## 3. 发现新值不代表获准修改

金额不同可能是另一票、另一行、识别错误或真正修改。当前更新需要唯一旧账及原文明示的编辑意图，未授权字段保留原值，缺失不是清空。清关 “clear cargo” 与清空付款字段必须区分；单纯词面命中只能作为候选提示，真正应用仍须逐字段证据。

## 4. 交易角色比公司名称更关键

通知方、收货人、邮件发件人、品牌抬头和银行收款人并不总是开票方或付款方。公司名称出现并不能单独证明 AR/AP。当前要求明确记账主体和可证交易关系，别名需显式配置；真实样本里关系不明时保留 null，避免“测试公司”被当成有业务角色的法人。

## 5. 金额、税和汇率需要明确范围

使用 Decimal 并以 JSON 数字导出，避免二进制浮点和浏览器大整数舍入。合计、税、折扣、已付和余额分别建模，合计不另生一笔费用；各币种分开核对。只有 `$` 不能唯一确定 USD；跨币种汇总还需明确汇率、时点与舍入政策，不能擅自换算。

## 6. 贷项和冲销应保留原账关系

负金额不一定代表应付或应收方向翻转。当前按原付款方/收款方及明确贷项、冲销关系决定方向和符号，一次性应用符号，防止重复翻转。没有原账关联时不能用金额正负猜业务含义。

## 7. 人工复核需要独立的批准机制

“已核对”备注只是跟进事实，不能充当授权变更凭据。当前不因打勾而把待复核写入有效账本。后续多人版本需要批准人、理由、补充材料、原始快照、变更集合、复核时间和撤销历史，采用事务提交，而不是直接编辑导出的 JSON。

## 8. 超时后的自动重试可能重复收费或建账

读取超时可能发生在外部服务已完成处理之后。当前不自动重发不确定 OCR 请求或整票任务，保留明确错误码；模型结构修复次数有限。后续外部服务若提供幂等键或查询任务状态，可优先查询，避免重新提交。账本业务幂等与外部 API 计费幂等是两个问题。

## 9. 高测试分数需要说明分母与数据来源

费用行、字段、operation 和可自动处理结果分别评分。模型漏行或结构错误不能缩小分母；全部返回复核也不能获得自动化满分。当前公开案例由助手构造，OCR 为固定输入，标签未经独立业务签核；阶段 9 真实材料测试另行报告。后续应扩大真实版式覆盖并让业务人员独立复核标签。

## 10. 单机安全边界与生产边界不同

本地网页使用 loopback、同源校验、会话令牌及下载允许列表，密钥保存在服务器端。私人材料和日志不进入 Git/ZIP。生产部署还需要登录、权限、加密、审计保留期、脱敏、供应商数据处理约定和共享账本并发控制；当前交付不宣称已经具备这些能力。

## 11. 可复现性需要同时冻结输入和程序

相同文件在不同模型、提示词、OCR 或规则版本下可能产生不同结果。当前缓存按配置与版本隔离，归档保留原始模型响应，交付包逐文件校验。历史验收不因新增网页而改写；公开留出一旦用于修复，就成为回归数据，不能重复称为全新未见验收。
