# 从空项目到完整交付的实施计划

当前阶段 0、1、3、4、5 已完成，见各阶段交付记录。阶段 2 已接通模型与指定 OCR，识别质量问题仍跟踪；阶段 4 完成候选提取，阶段 5 的 63/63 规则案例、真实费用 7/7 行和三份账单的合计均通过，详见 [阶段 5 验收](stage5-report.md)。下一步为阶段 6：匹配、去重和增量更新。最终业务流水线尚未实现。基准未经过独立业务人员签核。数字门槛为内部验收标准。

每个阶段记录产出、代码版本、实际命令、通过数、失败项与报告位置。未通过不能标记该阶段完成；可以继续不依赖阻塞项的工作，但不能用模拟成功替代真实接入验收。详细计算规则见 [评测规范](evaluation.md)。

## 最终能力与技术边界

- 使用 Python 和 LangChain，支持 EML、PDF、JPG/PNG/TIFF、XLS/XLSX、DOC/DOCX 和旧账单 JSON。
- 输入材料、当前记账主体及可选旧账单，输出题目要求的 JSON 数组和独立运行清单、审计记录。
- 支持 CREATE、UPDATE、NO_CHANGE、PENDING_REVIEW，不直接操作外部财务账本。
- PDF、图片必须接入题目指定 OCR，本地提取不能替代接口验收。
- 先完成可运行、可评测的 CLI，演示页面作为核心完成后的可选增强。

```text
输入检查 → 多格式解析 / 指定 OCR → 带来源的文档片段
→ LangChain 结构化提取 → 标准化与校验 → 旧账单匹配
→ 增量变更与 AR/AP 判断 → 最终校验 → JSON、审计记录与报告
```

## 阶段 0：明确需求、数据模型和正确答案

**具体工作**

1. 将题目逐项映射到模块、用例和交付文档，建立需求覆盖表。
2. 盘点 4 个真实顶层文件及邮件附件，记录哈希、页数、附件关系和来源。
3. 人工核对实际费用、合计、运输信息、通用条款和不确定字段，建立基准答案。
4. 定义核心输出结构，以及原始费用名、标准名、数量、单价、运输标识和字段证据等补充信息。
5. 明确记账主体、公司别名、费用行身份、修改意图、缺失值和金额规则。
6. 规划至少 60 个标明来源的业务场景，按来源分组划分开发/验证/最终验收集。

**产出**：需求覆盖表、数据契约、真实样本清单及人工答案、模拟场景和划分清单。

**放行条件**

- 题目要求 100% 有实现位置和验收方式；真实文件与相关附件全部登记。
- 实际费用行全部人工核对；可确定字段有答案，未知字段有原因，不猜币种或 AR/AP。
- 明确保留同单两行 Handling Charge，不把通用收费条款当作本次费用。
- 先固定数据划分和评分规则，再优化提示词。

## 阶段 1：搭建工程和最小测试骨架

**具体工作**

1. 确定 Python 版本，建立虚拟环境、`pyproject.toml` 和可复现依赖锁定文件。
2. 划分解析、OCR、提取、领域规则、工作流与评测模块。
3. 定义文档片段、候选费用、最终记录、变更计划和错误类型的结构化模型。
4. 建立配置、`.env.example`、日志和 CLI；密钥不写进代码或日志。
5. 建立 pytest 及最小评测命令，能加载一个案例、比较答案和生成报告。
6. 区分正常输出、待复核结果和程序级失败，避免失败被伪装为成功空数组。

**产出**：可安装的包、CLI 帮助、配置模板、模型、测试和评测骨架。

**放行条件**

- 新虚拟环境按 README 安装成功，包可导入，CLI 帮助正常。
- 合法模型通过；错误结构、非法 operation 和字符串金额被拒绝。
- 无真实密钥也可运行离线测试，缺少在线配置时明确报错。
- 测试和评测命令正确反映失败，报告有分子分母和失败项。

## 阶段 2：验证真实 OCR 和大模型接入

**具体工作**

1. 接入指定 OCR `http://36.103.199.11:5002/process`，按题目传入参数。
2. 确定可访问文件 URL 的提供方式；如需上传，采用可配置适配器，并说明有效期和清理方式。
3. 用真实 PDF 和 PNG 验证响应形态、多页结果、文本及表格，保留本地原始响应。
4. 实现超时、状态错误、无效 JSON、空结果处理和有上限的重试；不假设服务提交天然幂等。
5. 通过 LangChain 接通可配置模型，验证一次结构化提取并记录模型/提示词版本。
6. 提供明确标记的缓存和离线回放，用于测试，不冒充实时调用。

**产出**：OCR 客户端、响应适配器、模型适配器、回放接口和真实接入记录。

**放行条件**

- 一个真实 PDF、一个真实 PNG 各至少一次指定 OCR 成功，内容可用。
- 至少一次真实 LangChain 模型调用返回符合约束的结果。
- 超时、服务错误、畸形/空响应等故障用例全部被识别，不生成有效账单。
- 本地路径不能当作远程 URL；缺配置或服务不可达明确失败，不能降级后谎报成功。

若外部依赖阻塞，可继续本地解析与确定性规则开发，但本阶段保持未通过，最终交付前补齐真实验收。

## 阶段 3：完成多格式文档解析

**具体工作**

1. EML 提取邮件头、纯文本/HTML 正文、附件及嵌套邮件，避免正文重复。
2. 按扩展名和文件特征识别真实格式；现有 EML 中 MIME 为 `application/octet-stream` 的 PDF 仍须正确处理。
3. 内嵌图片保留来源后分类，不仅凭 CID 或文件名丢弃可能的业务图片。
4. PDF/图片接 OCR，保存页码、表格和片段位置，覆盖扫描、多页和 TIFF。
5. Excel 保留工作表、单元格、费用行及公式/缓存值；无缓存公式明确处理，不能静默当作有效金额。
6. Word 提取段落和表格，明确 DOC、XLS 的兼容依赖，并能在交付环境复现。
7. 处理损坏文件、递归深度和大小限制，输出明确错误状态。

**产出**：各格式解析器、统一文档片段、格式和边界场景报告。

**放行条件**

- 每种要求格式至少一个有效文件解析成功，DOC/XLS 不以“不支持”视为完成。
- 真实 EML 的正文、两个 PDF 和一张内嵌图片全部发现、分类并保留关联。
- 人工标注的关键文本和费用表行保留率 100%，来源可定位到附件/页或单元格。
- 错误 MIME、损坏文件、嵌套附件、公式无缓存等用例全部得到预期状态。

## 阶段 4：结构化提取与首个业务闭环

**具体工作**

1. LangChain 提取单据、双方、运输标识、费用、数量、单价、金额、币种和付款描述。
2. 联合正文与附件，逐字段保留证据，区分实际费用、合计、已付金额和一般条款。
3. 保留原始名称，缺失字段用 null，材料中的指令不能改变系统规则。
4. 模型结构错误允许有限修复，仍失败则保留记录并返回明确状态。
5. 先跑通一个真实费用样本到候选 JSON，再扩展全部材料。

**产出**：提取链、提示词版本、候选记录和第一份提取评测报告。

**放行条件**

- 成功输出结构合法率 100%，失败样本不从业务指标分母消失。
- 真实材料已确认费用行全部保留；两行 Handling Charge 不合并，合计和条款不生成额外费用。
- 固定验证集费用行 precision/recall 均 ≥90%，关键字段准确率 ≥90%。
- 已输出非空关键字段的证据可定位率 100%，不要求未知值凭空有答案。

## 阶段 5：标准化、金额校验和 AR/AP

**具体工作**

1. 建立费用名称词表，保留原文；未知名称不强行分类。
2. 校验 ISO 4217 币种，不把无上下文的 `$` 一律变成 USD。
3. 区分 PP/CC、COD 和付款期限，无法可靠映射时保留原文及 null。
4. Decimal 运算，按币种及事先定义的舍入规则检查数量×单价、税、小计和总计。
5. 覆盖借贷项、负数、折扣和多币种，禁止无汇率直接合计不同币种。
6. 按记账主体、双方和收费方向判断 AR/AP，覆盖贷项、冲销及负数，避免重复翻转方向。
7. OCR 字符混淆只在有依据时纠正，否则复核，不盲改标识符。

**产出**：标准化词表、校验器、财务方向规则和复核原因。

**放行条件**

- 名称、金额、币种和付款规则用例全部通过。
- 明确方向的 AR/AP 规则用例正确率 100%，包含双方视角、贷项和冲销。
- 设计的关键金额冲突、未知币种、未知主体场景 100% 拦截或复核。
- 无证据补全核心字段次数为 0，明确可处理场景不能无理由全部复核。

## 阶段 6：匹配、去重和增量更新

**具体工作**

1. 验证旧账单 JSON，定义稳定账单/费用行身份。
2. 按题目优先级组合匹配，输出依据；多候选不得任取一条。
3. 同名费用保留行身份，不能消歧则复核，不能按名称直接去重。
4. 分离“发现新值”和“明确请求修改”，生成旧值、新值、证据和意图的变更清单。
5. 只合并授权字段，未修改的旧值及扩展字段保留；缺失 null 不自动清空旧值。
6. 输出四类 operation，验证同文件、同内容不同名以及多来源重复。
7. 将结果应用到旧账单快照后重传，验证不重复新增、不重复修改。

**产出**：匹配器、去重、变更计划、合并模块和四类操作示例。

**放行条件**

- 至少 40 个确定性业务用例全部通过，覆盖各级匹配、同名行、多候选、显式清空和字段继承。
- 未授权覆盖、错误选中旧账单、同名误合并和重复创建次数均为 0。
- 幂等用例通过率 100%，可自动处理的明确新增/更新得到正确操作。
- 不能以全部返回 PENDING_REVIEW 绕过业务测试。

## 阶段 7：串联工作流和可用 CLI

**具体工作**

1. 将解析、OCR、提取、规则、匹配、变更和输出串成明确状态流程。
2. CLI 接收文件/目录、URL 映射、记账主体、旧账单、配置和输出路径。
3. 支持多文件和部分失败，每个输入在运行清单中都有成功/待复核/错误状态。
4. 输出合法核心 JSON 数组，运行元信息和审计记录另存，保持题目结构兼容。
5. 审计记录给出来源、规则和简短可核对依据，不要求冗长内部推理。
6. 缓存区分文件及 OCR、模型、提示词和规则版本；在线/回放模式明确标记。

**产出**：完整 CLI、工作流、结果文件、运行清单、审计日志和端到端演示。

**放行条件**

- 新增、更新、重传、复核、混合批次及格式全覆盖的端到端必过案例全部符合预期。
- 输入登记率和成功记录可追溯率均为 100%，没有静默遗漏文件或费用行。
- 核心 JSON 可被标准解析器与数据模型验证，程序故障和正常待复核有文档化退出码。
- README 命令可复现，无需修改源码绝对路径。

## 阶段 8：完整 harness 与质量验收

**具体工作**

1. 完成至少 60 个业务场景及独立的规则测试覆盖；逐组评测格式、操作、真实/模拟和可判定字段。
2. 注入 OCR 故障、模型结构错误、矛盾信息、无效旧账单、损坏文件和材料指令干扰。
3. 固定版本对验证集做 3 次独立模型调用，比较业务结果；候选缓存不能代替重复调用。
4. 冻结版本后运行最终验收集，生成逐项差异、实际分子分母和失败原因。

**放行条件**

- 关键规则和端到端必过用例全部通过。
- 验证集和最终验收集分别达到：费用行 precision/recall ≥95%、关键字段准确率 ≥95%、operation 正确率 ≥95%。
- 可自动处理费用行的自动正确完成率 ≥90%；已接受结果核心正确率 100%。
- 设计的关键风险拦截率 100%；未授权覆盖、重复建账、旧账单误选、错误接受金额/币种/AR/AP 均为 0。
- 真实材料已确认的费用、金额和明确币种全部正确，未知信息未擅自补全。
- 3 次业务一致率 ≥95% 且每次无严重错误；固定响应回放业务一致率 100%。
- 报告提供实际计数和失败清单；小样本高分不能宣称生产总体准确率。

## 阶段 9：干净环境验收与交付

**具体工作**

1. 完成安装、配置、文件 URL 准备、CLI 示例、在线/离线差异和故障排查文档。
2. 整理架构、harness、实际评测报告和标准输出示例。
3. 写至少 5 点补充思考：费用行身份、证据冲突、更新意图、税和币种、人工复核、成本或可追溯性。
4. 检查打包范围，提供模拟演示数据和真实样本本地导入方式，不打包密钥或临时敏感日志。
5. 从 ZIP 在新虚拟环境安装并运行离线演示/测试；配置就绪时执行完整在线演示。
6. 生成 ZIP、版本与文件清单；恢复 Git 网络后验证远程读写，按交付需要提交推送。

**最终完成条件**

- 干净环境可按文档复现，无未说明的转换软件或开发机路径依赖。
- 离线验收全部通过，指定 OCR、LangChain 和完整在线流程有实际成功记录。
- 阶段 8 门槛全部满足，限制和阻塞项如实说明。
- ZIP 完整或仓库对应版本可获取；配置 remote 不等于已推送。

## 后续推进方式

每次推进一个可验收阶段，完成后提供产出、实际测试命令、通过数和剩余问题。出现实质业务修复时补回归案例；已通过检查只在相关变动或新疑点出现时重跑。

外部依赖未就绪不影响独立模块工作，但不能把阻塞阶段标成完成。出现关键字段误接受或不正确更新时，修复后重跑相关用例及必要的阶段检查，再进入下一步。
