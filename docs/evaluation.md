# 评测规范

本规范定义后续如何验收，不代表已有测试结果。数字门槛是本项目的内部目标，并非题目给出的额外指标。

## 1. 数据集与人工答案

- 当前 4 个顶层真实文件及邮件附件：人工核对后用于回归；开发时已看过，不宣称为未见测试集。
- 至少 60 个独立标注的业务场景：开发 30、验证 15、最终验收 15；每个场景可以含多文件、旧账单和多行费用。
- 至少 40 个确定性规则用例：直接输入人工确认的候选字段，不调用模型，验证财务、匹配、更新和幂等规则。不能替代端到端评测。
- 真实数据与 synthetic 数据分别报告。相同模板、同票运输材料、原始材料及其格式/金额变体按 family_id 分组，不跨集合拆分。
- 最终验收集在开发前分组留出，材料和答案不用于优化提取链或提示词。验收失败后若使用其案例调优，则原案例转为回归数据，并补充未见案例重新独立验收。

每个场景的答案包括：来源、family_id、文件、记账主体、旧账单、实际费用行、关键字段、字段证据、预期操作、AR/AP、授权变更集合、应继承字段、是否可自动处理，以及应复核的具体原因。

目标答案应由业务人员独立复核，不以待测提取链自评作为正确标签。目前阶段 0 的工作基准由助手对照原文/页面编制，明确记录未独立人工签核；它用于开发和资料检查，不能宣称独立人工标注质量。字段区分可确定、缺失、矛盾和不可辨认；不能为了有答案而猜测 `$` 的币种或 AR/AP。

## 2. 费用行与字段的评分

先根据标注的来源区域、费用行身份、运输关联和原始描述做一对一匹配，再比较金额等字段。不得仅凭相同金额认定同一费用，也不得只凭名称合并两行 Handling Charge。

同一费用在正文和附件重复出现只计一次；两项实际费用即使同名或同额仍计两行。不能唯一对应时人工核对评分差异，不任取有利匹配。

| 指标 | 计算方式 | 最终门槛 |
|---|---|---|
| JSON/Schema 合法率 | 合法成功输出数 / 成功输出总数 | 100% |
| 费用行 precision | 正确对应实际费用的输出行数 / 输出费用行总数 | ≥95% |
| 费用行 recall | 正确对应的实际费用行数 / 预期实际费用行总数 | ≥95% |
| 关键字段准确率 | 正确关键字段槽位数 / 预期可判定关键字段槽位数 | ≥95% |
| 操作类型正确率 | operation 正确的行数 / 预期业务行总数 | ≥95% |
| 自动正确完成率 | 自动输出且核心字段与变更全部正确的行数 / 标注可自动处理的费用行数 | ≥90% |
| 已接受结果核心正确率 | 自动接受且核心值全部正确的行数 / 自动接受行数 | 100% |
| 关键风险拦截率 | 正确复核/拒绝且原因命中的风险场景数 / 预期关键风险场景数 | 100% |
| 未授权字段覆盖数 | 更新改动集合超出明确授权集合的字段数 | 0 |
| 幂等通过率 | 重传未新增费用或重复变更的场景数 / 幂等场景数 | 100% |
| 证据可定位率 | 有有效材料定位的非空关键字段数 / 输出非空关键字段数 | 100% |
| 重复调用业务一致率 | 3 次预测业务字段完全一致的标签行数 / 参与重复验证的标签行数 | ≥95% |

关键字段是费用金额、币种、费用项、单据编号和交易双方。已接受结果的核心值还包含 operation、记账主体、AR/AP 和实际变更。AR/AP 另列明确方向正确数、可判定总数及未知场景处理结果。

## 3. 不允许掩盖错误的计分规则

1. 漏行、运行失败、已知字段返回 null 都不能从分母删除。运行失败仍计入对应的预期费用和操作分母。
2. 费用行检出正确但金额错误，行检出可以得分，金额与自动正确完成不得分。
3. 多输出的行计为误报，即使它被标为 PENDING_REVIEW。
4. 对可自动处理的行全部输出复核，不能通过自动正确完成率门槛。
5. 缺失字段正确输出 null 计入缺失处理检查，不让大量 null 抬高可判定字段准确率。
6. 无实际费用的失败文件写入运行清单，不伪造一条空费用。文件状态与异常识别正确率要求 100%。
7. 指标分母为 0 记 N/A，不能视为 100% 或该能力已验收，必要时补样本。
8. 验证集和最终验收集分别计分；按真实/模拟、格式和操作类型报告，不用开发成绩稀释失败。
9. 结果写出前同时执行字段和业务校验；schema 合法不能代替业务正确。

## 4. 数值与文本比较

- 金额按 Decimal、币种精度和预先标注的舍入方式比较。没有舍入说明的基准金额要求数值相等。
- 合计校验容差在用例中事先固定且有依据，不能测试失败后放宽，也不对所有币种统一容忍 0.01。
- 日期统一格式后比较，有歧义时保留原文并复核。
- 币种三字码精确比较；标准费用名称按词表比较，同时检查原始名称保留。
- 公司名只用预配置别名归一化，不用宽松相似度掩盖交易方错误。
- 单号、提单号和箱号不允许模糊评分掩盖字符错误。
- 字段继承比较完整业务内容，包括旧记录扩展字段；审计时间戳不参与重复运行一致性比较。

## 5. 必须覆盖的测试类别

| 类别 | 必须覆盖的情况 |
|---|---|
| 格式 | EML、嵌套邮件、文本/扫描/多页 PDF、PNG/JPG/TIFF、XLS/XLSX、DOC/DOCX |
| 解析 | 错误 MIME、纯文本/HTML、内嵌图、表格、多工作表、公式无缓存、损坏文件 |
| 提取 | 多费用、同名多行、合计/税额/已付金额、通用条款、正文与附件互补 |
| 付款 | PP/CC、FREIGHT PREPAID、COD、含糊货币符号、未知币种、多币种 |
| 财务 | 双方记账视角、未知主体、Debit/Credit Note、负数、冲销和折扣 |
| 匹配 | 题目各级组合、多个候选、同单同名行、跨文件重复、不同单同金额 |
| 更新 | 只改金额、只改付款描述、明确清空、缺失不覆盖、扩展字段继承 |
| 幂等 | 同文件重传、同内容不同文件名、更新应用后重传、多来源重叠 |
| 故障 | OCR 超时/错误/空响应、模型无效 JSON、无效旧账单、缓存版本变化 |
| 材料指令干扰 | 邮件/附件要求忽略规则、伪造金额或改输出格式，仍按业务规则处理 |

至少 40 个规则用例及 60 个业务场景只是规模下限，不能替代类别覆盖。重复运行同一用例不算新增独立案例。

## 6. harness 如何运行

1. 案例加载器读取文件、配置、旧账单、标签和数据分组。
2. 运行器区分 live 与 replay，记录 OCR、模型、提示词和规则版本、超时、重试与缓存命中。
3. 逐项比较 schema、费用行、字段、操作、变更集合和证据来源。
4. 失败归类为解析、OCR、提取、规则、匹配或标签问题，保存逐项差异。
5. 输出 JSON 报告和易读表格，保存代码/数据版本、实际调用数、各项分子分母及失败清单。
6. 平时运行与改动相关的检查，阶段验收和最终交付运行必要的完整套件。

对固定版本的验证集执行 3 次独立模型调用，不用候选输出缓存假装重复验证；OCR 可使用固定响应以隔离模型变化。固定响应全流程回放的业务结果应完全一致。

耗时和成本先实测，再设合理预算，不在服务尚未接入时承诺固定速度。

## 7. 最终放行

全部确定性关键规则与必过端到端用例通过；验证集及最终验收集分别达到适用指标；真实样本已确认的费用、金额和明确币种全部正确；未知信息没有擅自补全。

3 次验证运行都不能出现严重业务错误。任一次未授权覆盖、重复建账、旧账单误选、错误接受关键金额/币种/AR/AP 均阻止放行。

此外必须有指定 OCR、LangChain 模型和完整在线流程的真实成功记录，以及干净环境安装和离线验收记录。仅有模拟或回放不能视为在线能力完成。

所有百分比同时展示实际计数，例如 19/20。小样本内通过不代表已证明真实生产总体具有同样准确率。不能通过删除失败用例或临时放宽规则使版本合格。
